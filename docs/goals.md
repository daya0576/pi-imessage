# iMessage /goal（第一方源码 MVP）

没有安装任何同名 pi-goal 包，也没有启用扩展发现。保留 `noExtensions:true`，通过已安装 Pi SDK 的受控 `extensionFactories` 注册 `goal_inspect` 和 `goal_report`。这不是 TUI 插件；实际部署状态以发布记录和线上验证为准。

## 聊天命令

- `/goal <目标>`：接纳时立即隔离旧工作、记录当前聊天的新目标为等待执行；在 SDK 旧操作与取消都结算后，才在正常聊天上下文开始执行。不是只保存字符串。目标最多 2000 字符。
- `/goal`、`/goal status`：不调用模型，立即显示目标、等待/执行/暂停/阻塞/完成状态、最近报告的进展、阻塞原因、报告的验证依据、已用轮数/预算。执行中也能查询。
- `/goal pause`：立即隔离当前目标轮次，暂停并请求取消；普通消息不会恢复。
- `/goal resume`：显式恢复暂停/阻塞目标；正在等待/执行时重复调用不创建第二个执行器。不会增加预算。恢复时要求先核对未知操作结果。
- `/goal clear`：立即写入清除标记并请求取消。检查点中的目标/进展/依据被清除，但不会删除聊天日志或 SDK 历史。
- `/stop`：暂停目标自动执行，同时停止当前模型工作。后续普通输入仍按原队列处理。
- `/new`：隔离并暂停旧目标；只有 SDK 取消确认后才替换会话。保留目标供 `/goal status` 检查；不会在新会话自动恢复。
- `/reload`：先取消并暂停目标，再在聊天 ownership 下更新模型；需要显式恢复。

控制命令仍按接收顺序通过日志、自回声与回复权限过滤，然后同步隔离/变更状态。接纳与 SDK 取消、回复发送的等待分离：一个取消或发送尚未结束，不会挡住后续同聊天或其他聊天的 `/goal status`、pause、clear、`/stop`。替换目标不会在异步取消返回后重新创建，迟到的旧命令回复会被新变更隔离。命令本身的附件预处理仍沿用既有 pipeline；不保证磁盘或消息传输故障时回复瞬时到达。

`status/pause/resume/clear` 是保留子命令，不接受额外参数。不支持预算 flags。预算耗尽后只能在检查结果之后，由用户明确创建新目标；模型工具不能创建、恢复目标或增加预算。

## 执行与隔离

固定累计 **4 次外层 prompt 调用**，包括已开始但被打断的调用；尚在 ownership 等待的调用不计费为一轮。这不是 SDK 的单个 tool/assistant turn 上限，也不是 token 预算。不报告估算 token 或把上下文 tokens 当工作量。

沿用现有消息批处理队列的 idle 回调，每次只执行一轮；先处理已排队的真实输入。agent manager 在实际 admission 前再次让位给已排队输入，包括其他正常调用者。每次调用独立经过原有活动超时、前台总时限、压缩事件及专用压缩时限。没有 `agent_end` 递归 prompt、额外调度服务、定时任务或后台子进程。目标超时及异常后保留 SDK ownership，直到原操作与 abort 都结算；不能在未知工具操作仍未结算时另起竞争轮次。启用目标控制器的正常聊天中，穿插的普通输入超时/异常也暂停目标并保留 ownership，即使暂时还没有目标，也不会丢弃未知操作的会话后让新目标竞争同一 context.jsonl。普通超时仍保存中断检查点、不自动重试；显式 resume 也必须等原操作和 abort 都结算，之后仍先处理真实排队输入。隔离的只读/ephemeral 调用不受此聊天目标策略影响。

穿插的普通轮次收到不成功的 `compaction_end` 时立即暂停聊天目标，不依赖 SDK 抛异常或等待超时；即使 `prompt()` 正常返回也不会继续自动目标。普通输入仍可排队处理，恢复目标必须显式 `/goal resume`。

目标只通过正常、可写聊天会话的 admitted capability 暴露给工具。ephemeral/sessionKey/read-only 会话不注册目标工具；普通轮次也不能调用它们修改目标。工具没有 chatGuid、目标创建或预算修改参数。报告必须携带本轮 `goal_inspect` 给出的 generation。每次命令替换/暂停/清除和每轮执行使用新 generation，旧工具报告和旧输出不能提交到新轮次。目标文本是用户级不可信数据，不是新的系统指令或授权。

`goal_report` 可报告实质进展、立即阻塞或完成。完成必须提供非空验证依据，且外层调用正常完成后才提交完成状态；压缩失败、异常或取消不能提交待确认的完成。依据是**模型报告，不是独立证明**。缺少权限/输入应首次就报告 blocked，不等待三次失败；blocked/completed 后工具 gate 拒绝后续工具。没有报告新进展（进展文本与上一轮相同）就暂停；4 轮用尽暂停，绝不自动续增。

进展输出使用仍有效、被 await 的 sender/log/store end tasks，不复用已经结束的命令 pipeline 的 emit。保留聊天/群名称、自回声过滤和日志记录。每次目标输出检查 generation、worker 运行状态和 reply allowlist/blacklist；发送失败暂停后续自动执行，不自动重发。发送接口成功只代表发送调用接受，不代表收件人收到或读到。开始发送后发生取消，无法撤回已经交给传输层的消息。

## 持久化与重启

每聊天 `WORKING_DIR/<chatGuid>/goal.json`，版本 1；独占创建随机临时文件、权限 0600，再原子 rename。目标/报告字段有长度限制，读取文件最多 64000 字节，拒绝非法路径及符号链接。清除使用 tombstone。损坏/不支持版本的状态拒绝创建和恢复，要求人工检查，不把损坏当作新任务授权。

任一检查点写入失败都会立即在内存中换代并暂停，不重试写入；初始轮次检查点失败也让 idle 回调返回 false，不消耗轮数、不启动 SDK、不循环重试。后续 status 或普通消息也不能隐式恢复。`/goal status` 可查询存储故障说明；失败当时不保证自动发出新的状态通知。磁盘可能保留较旧检查点或未 rename 的临时文件，不能声称暂停已持久化；应检查实际结果并修复存储后显式恢复。

状态惰性读取。重启后遇到 ready/running 检查点，一律改为 paused，提示未知副作用；启动不扫描或重放目标。已暂停/阻塞/完成状态可供检查。必须由用户明确 `/goal resume`，并先核对检查点、真实进程/结果及必要的授权。这只是 fail-closed 检查点，不是通用自动崩溃恢复、事务回滚或 exactly-once 工具执行。

## 已知限制

- 单 worker 所有权模型，不能让多个 worker 同时写同一聊天状态；shadow 不启动 bot，因此不执行目标。未新增跨进程锁、热迁移或多实例协调。
- 继承正常聊天已有的主机工具权限，不是新的沙箱。模型对缺少权限、实际进展与副作用是否发生的判断不是独立验证；无法语义识别所有重复操作或恶意改写进展。每轮 SDK 内可能有多次工具调用，仍受原超时约束；无全局 token/cost 上限。
- 没有自动副作用重试。abort 不能撤销已发生的工具操作；SDK 永不结算时，同聊天排队输入仍等待，需人工检查。取消命令先获准隔离，回复可能等待既有 10 秒取消确认窗口（排在其他取消之后的确认可能更久），但不占用控制命令接纳队列；不能承诺瞬时中止主机操作。
- 不支持跨聊天共享目标、Web 目标入口、自动任务恢复、自动预算延期。新会话恢复只使用保留的检查点及新上下文，旧 SDK 对话已按 `/new` 语义清除。
- 文件 rename 提供进程级原子替换，不声称断电级 fsync 保证；允许的状态不会包含完整历史。聊天及 SDK 日志仍保留已有信息。
- 功能回归使用可控 SDK/发送器 mock，不代表真实用户任务或收件人送达已验证。发布流程另行执行模型健康检查；它也不等同于实际目标验收。

## 验证与交互审查

`src/__tests__/goal-runtime.test.ts` 经过真实 command transport、批处理、agent manager ownership 和受控扩展工厂，使用可手动结算的 SDK prompt/abort 与 sender mock。覆盖两步目标、busy status、普通输入优先、内部调用者让位、实际 sender/log/echo、非空依据、迟到报告、stop/pause/clear/new/replacement/reload、重复 resume、阻塞/无进展/耗尽、压缩失败、未知超时、发送失败、聊天与只读隔离、worker/回复 gate、重启不重放、损坏/路径/预算参数。

修复回归还覆盖：替换取消未结算时连续 status/pause/new/clear/stop 与另一聊天照常接纳；发送器未结算不堵接纳；穿插普通输入超时、保留中断检查点、迟到输出隔离、prompt 先结束而 abort 未结束时不启动新轮次，最终结算后真实输入仍优先。

存储与压缩回归覆盖：初始运行检查点写入失败时 idle 返回 false，存储恢复后 status/普通输入也不会触发重试，只有显式 resume 才开始一轮；穿插普通输入的压缩失败立即暂停目标，即使 SDK 正常返回也不自动继续，迟到输出被隔离，显式恢复后完成第二步。

批处理 drain 保留并合并执行期间的新唤醒请求。SDK 失败后的状态发送尚未结算时，显式 resume 或替换目标不会丢失唤醒；旧发送结束后重新检查最新状态，无需再发一条消息。两条 transport 回归分别验证 resume 和 replacement；旧代码均在“未启动第二轮”断言失败，修复后各启动一次并完成目标。
